# Research candidates and questions

This October 9 intake separates other people's results, source inspection and proposals for Rocinante. None of the candidates below was installed or benchmarked on Rocinante as part of this publication. Our measured baseline is in [the measurement note](MEASUREMENTS-2026-10-09.md).

## Swift 1.5 IQ3_S: test task time and quality

The new [Swift 1.5 GSQ-RCO model card](https://huggingface.co/ukisai/Swift-1.5-Qwen3.8-Flash-Next-GSQ-RCO-GGUF) includes IQ3_S weights totaling 83,743,737,120 bytes. Quantization divergence is against Swift BF16; it does not compare Swift's capability with original Flash-Next.

[Strata issue 1586](https://github.com/Niko1221/Strata/issues/1586) reports two 3090s, one on PCIe 4.0 x16 and one on a chipset x4 link, without NVLink. Five sampled coding runs after warm-up, with 1,500-token generations, averaged 138 tok/s; trimming stage weights reached 142.4 tok/s. An approximately 75K-context run reached 100–104 tok/s. Later, two approximately 76K conversations fell to 16.1 tok/s each. Single-request speed is not a concurrency result. [Issue 1651](https://github.com/Niko1221/Strata/issues/1651) records setup/packaging limitations for Swift IQ3_S.

**Proposed check:** original IQ3_S versus Swift IQ3_S on completed coding/review tasks at medium and xhigh effort, with matched prompt depth and enough output allowance. Compare task pass rate, time, reasoning length and cache behavior. Shorter reasoning is the hypothesis; equal capability is not established.

## Existing 4070 Ti Super as a peer expert tier

[Issue 1643](https://github.com/Niko1221/Strata/issues/1643) reports a modified 2080 Ti 22 GB plus an RTX 5050 8 GB without GPU P2P. With Swift IQ2_XS, a 31,358-token prompt preceded a 256-token decode at 55.8 tok/s, with 91.1% expert-cache hits. This is one short decode at a lower quality tier.

Peer-assisted long prefill triggered CUDA faults including Xid 31. Setting `--peer-prefill-rows 0` completed that prompt while retaining peer-assisted decode. A first Rocinante experiment should start with that reported workaround and ordinary CUDA behavior, then validate state and quality before speed.

**Open question:** for asymmetric 48+16 GB cards, does whole-layer placement, an independent helper/cache, or peer expert placement win at IQ3_S and UD-IQ4_XS? Measure actual PCIe topology, peer support, transfer overhead and long-context behavior. Do not predict speed by adding VRAM capacities or the cards' standalone tok/s.

## GLM-5.3-Flash: a separate engine and CUDA port

Inspected [OpenMOSE/Strata-GLM-AMD at `6c71ff0`](https://github.com/OpenMOSE/Strata-GLM-AMD/tree/6c71ff0d84f1543747ef9bc8451d56bcba3cccf7). Its report uses a 117.5 GB GSQ-RCO 3-bit pack with Q2_K experts: two 48 GB W7900s achieve 30–34 decode tok/s with MTP, one achieves 15–16, and two achieve 1,060 prefill tok/s at 128K. Configured context is 262,144. Needle checks through 236K are not broad coding validation.

This is a 45-layer, 288-expert-per-layer MoE path with different active work and attention machinery; comparing it with Flash-Next is not a dense-versus-MoE explanation. NVIDIA execution is explicitly untested. The published path retains the learned indexer; “indexer-free” was a prospective alternative, and an earlier page-mean substitute failed 64K needle tests.

A CUDA-port hazard is visible in [the Q2_K expert kernel](https://github.com/OpenMOSE/Strata-GLM-AMD/blob/6c71ff0d84f1543747ef9bc8451d56bcba3cccf7/src/glm5/moe_q2k.cu): non-AMD kernel work is absent despite an availability path, while [the engine](https://github.com/OpenMOSE/Strata-GLM-AMD/blob/6c71ff0d84f1543747ef9bc8451d56bcba3cccf7/src/glm5/engine.cpp) selects Q2_K buffers. Validate or bypass that path (`STRATA_GLM5_NOQ2K=1`) and check the fallback before trusting CUDA output. No 50–70 tok/s projection for our cards follows from this AMD report.

## Radiance: native low-bit kernels and speculation

[Alex Miller's dual-R9700 article](https://alexkmiller.com/blog/2026/09/07/dual-r9700-llama-cpp-and-vllm.html) reports Qwen3.8-27B at 184.9 decode tok/s using Radiance MXFP4 and speculation, versus 19.2 with default llama.cpp Q8 and 29.7 in its tuned table. It changes engine, quantization, speculation and kernels. The article does not give the fastest row's actual prompt depth, output count or repeated-run distribution. A 256K configured maximum does not establish 185 tok/s at 100K.

The separately inspected [Radiance revision `45da506`](https://codeberg.org/ggz14/radiance-vllm-mxfp4/src/commit/45da5063820c887d88c6d74af9215e5ba14bd7b3) is not established as the article's revision. Its shape-specific GEMMs, fused operations, recurrent-state handling and speculative controller suggest experiments, not drop-in SM120 kernels. Its [performance notes](https://codeberg.org/ggz14/radiance-vllm-mxfp4/src/commit/45da5063820c887d88c6d74af9215e5ba14bd7b3/PERFORMANCE.md) also report a multi-turn failure of lazy recurrent-state handling after single-shot checks passed. This supports testing many follow-up turns and prefix-cache state, rather than accepting a speed win from one prompt.

**Our check:** native HF NVFP4 + DFlash already has a narrow 181.4 end-to-end tok/s result on Rocinante. Evaluate it on the long-context tool tasks before attempting an AMD-kernel port. Compare fixed-work kernel timing separately from model-output speed.

## Zyphra expert coupling: useful hypothesis, not an inference result

[Expert Coupling in MoE Pretraining](https://arxiv.org/html/2610.09372v1) studies correlated expert placement and token shuffling during distributed training. Co-selected experts share a device, so an activation can be sent once per destination. Earlier-layer routing guides token ownership through existing collectives. The token-shuffling result requires sequence-parallel tensor/expert parallelism; it is not a TP=1 mechanism.

The reported maximum is 1.41× end-to-end training speedup and 1.16–2.63× all-to-all improvement on multi-node MI300X systems. Weights and router choices remain unchanged. **Inference was not benchmarked.**

For Rocinante, possible applications are workload-aware placement across unequal GPUs and predicting cold experts early enough to overlap transfers. These are our hypotheses. Co-location's communication benefit does not automatically improve a single GPU's static frequency-cache hit rate, nor remove long-context attention cost.

**Minimal investigation:** record routing and expert-transfer waits without changing output; build co-activation and adjacent-layer conditional tables on one trace; evaluate predictions on held-out prose, code and tool turns. Prototype prefetch only if avoidable waits remain. Keep routing authoritative, retain miss fallback, and measure wasted bytes, VRAM occupancy, total task time and completed-answer quality.

## Questions worth answering before another broad sweep

1. At fixed accepted output work, what fraction of verification time is projections, expert compute, attention/state, graph/dispatch overhead and transfer wait? How does that change from 32K to 100K?
2. Can an SM120-specific kernel or fusion reduce the fixed step cost without changing outputs or cache/state semantics? Which exact shape is worth specializing?
3. Does predictive expert prefetch help when the hot cache already covers most requests, or does control overhead dominate? What held-out trace would settle it?
4. What is the cheapest placement experiment on the existing 4070 Ti Super, given its real PCIe link and unavailable/available P2P? Can it improve useful quality or capacity even if single-request speed falls?
5. How much task time can shorter reasoning and fewer cache re-reads save while retaining task correctness? Compare that with the plausible kernel gain.
6. Which stronger model/quant can preserve useful completed-task latency? Assess original IQ3_S, UD-IQ4_XS and Swift IQ3_S before proposing hardware purchases.

Any proposed production change needs a same-day control, sufficient output allowance, completed task checks, multi-turn state validation and a saved restoration path. These notes publish evidence and research questions; they do not promote a candidate.
